# Game internals used by the mod

Verified against the Steam build using Unity 2022.3.29 (Mono), decompiled with ILSpy (`ilspycmd`).
When a game update breaks the mod, check these first. Everything game-specific is in
`ObservationBuilder.cs`, `CampaignObserver.cs`, `ActionInjector.cs`, `EpisodeController.cs` and the Harmony
patch classes in `Env/`.

To decompile locally (never commit the output):

```bash
dotnet tool install ilspycmd --version 9.1.0.7988 --tool-path .tools
.tools/ilspycmd -p -o decompiled -r "<ULTRAKILL>/ULTRAKILL_Data/Managed" "<ULTRAKILL>/ULTRAKILL_Data/Managed/Assembly-CSharp.dll"
```

## Singletons
Most managers inherit `MonoSingleton<T>` and are accessed as `MonoSingleton<T>.Instance`. `GameStateManager.Instance` is a plain static property.

## Player: `NewMovement`
- `hp` (int, 100 max), `antiHp` (hard damage), `boostCharge` (float, 300 = 3 dashes), `dead`, `activated`, `sliding`, `levelOver`, `slowMode`, `playerCollider` (`CapsuleCollider`, 3.5 standing / 1.25 crouched)
- Private: `crouching`, `groundCheckPos` (the ground check's resting local position) — both read with `AccessTools.FieldRefAccess`
- `rb` (Rigidbody), `gc` (`GroundCheckGroup`, `.onGround`, `.heavyFall`, `.SetLocalPosition`)
- Movement input: `InputSource.Move.ReadValue<Vector2>()` in `NewMovement.Update`
- **Ground checks:** `gc` is a `GroundCheckGroup`, a thin aggregate over a `[SerializeField] private List<GroundCheck> instances`. It has **no** `ForceGroundCheck`; that method is on `GroundCheck` and must be called per instance (or `gc.GetComponentsInChildren<GroundCheck>(true)`). `GroundCheck` keeps `onGround` from `OnTriggerEnter`/`Exit` over a `cols` list, so a collider the capsule is **already** overlapping never re-announces itself — `ForceGroundCheck()` exists for exactly that: it clears `cols`, runs `Physics.OverlapCapsule` and replays `OnTriggerEnter` for each hit. Its `heavyFall` branch deals `x5000` damage to overlapping enemies and can `Bounce()`, which **teleports** the player, so clear `gc.heavyFall` before calling it.
- **The `slowMode` wedge.** `HandleSlideState` (private, called from `Update`) runs a stand-up test whenever `playerCollider.height != 3.5f`; when the raycast/spherecast above the player hits, it sets `crouching = true; slowMode = true;` and returns. Grounded that is an ordinary crouch. Airborne it is absorbing: `onGround` can never come back (above), `slowMode` blocks dash and stamina regen and cuts walk speed to `slowMode ? 1.25f : 2.75f` times `walkSpeed`, and `Update` re-applies `rb.velocity = gravityDirection * 100f` every frame while `gc.heavyFall` is set. Slide start is `(!slowMode || crouching)`, so sliding was never the blocked thing. `TryStartSlam` cannot re-enter (its condition ends `&& !gc.heavyFall`). Measured in 0-1: runs of 672 to 2976 consecutive decisions. `Env/TrainingSpeed.cs`'s `UnwedgePatch` postfixes `HandleSlideState` to break it.
- **A legitimate ground slam wears the wedge signature too.** `Update` calls `HandleInputs()` (:686) before the `heavyFall` block (:701) and `HandleSlideState()` (:740), so a slam started out of a slide is fully set up before the stand-up test runs in the same frame. `TryStartSlam` (:1108) calls `StopSlide()`, and `StopSlide` (:2448-2474) does **not** restore `playerCollider.height` — the stand-up in `HandleSlideState` does, on a later frame. So under a low ceiling the game sets `crouching`/`slowMode` on the very frame `heavyFall` and `rb.velocity = (0,-100,0)` are set, and `!onGround && slowMode` cannot tell a falling slam from the wedge on frame 1. `UnwedgePatch.HoldFrames` (config `unwedge_frames`) is the separator: a slam either lands or drops out of the ceiling's 3.5 m raycast within a frame or two, while the wedge holds forever. Cancelling it would cost `LandingImpact`, the ground-slam enemy damage in `GroundCheck.OnTriggerEnter` and `Breakable.Break(2f)` from `Update` (:708-716), and `heavyFall` cannot come back without a fresh Slide press with `slamCooldown == 0`.

## Speedrun technique fields (mod 0.8.0)

Read by `PlayerFields.cs`, `Obs/TechObserver.cs` and `Env/MovementPatches.cs`. **Every private field below is resolved with `AccessTools.FieldRefAccess` behind a try/catch and degrades to a neutral default with one logged warning**, so a rename costs that field, never the bridge. All are reads; nothing here writes.

- **`NewMovement.TrySSJ(Vector3 direction, float speedMultiplier, Func<int,float> speedLossFormula)`** — private, the whole reason macros exist. `bucket = (int)((jumpTimestamp - slideTimestamp) / 0.008)`; it returns early unless the gap is `> 0` and the bucket is `1..ssjMaxFrames-1`. It then **overwrites** `rb.velocity = velocityAfterSlide + direction × speedLossFormula(bucket) × speedMultiplier × walkSpeed × 2.75 × 3 × fixedDeltaTime`, preserves `y`, and clamps the magnitude to 100. Both call sites peak at bucket 1: `Jump` passes `1/2^(f-1)` and `WallJump` passes `(4-f+1)/4`, each 1.0 at f = 1. `MovementPatches` prefixes and postfixes it to read the bucket and the velocity either side.
- **`NewMovement.jumpTimestamp` / `slideTimestamp`** — **public `double`s**, set from `ctx.time` in `JumpPerformed` and `SlideCancelled`. `ctx.time` is the Input System event timestamp, sourced from the native wall clock: **`Time.captureDeltaTime` does not touch it**, so the SSJ window is real time and drifts with machine load. `SlideCancelled` records **only `if (sliding)`** — that single condition is why the wall macro needs an airborne slide.
- **`NewMovement.ssjMaxFrames`** — private, serialized, **4** in this build. Falls back to 4.
- **`NewMovement.velocityAfterSlide`** — private, written in exactly one place: `StopSlide`, as `dodgeDirection.normalized × max(24, preDashSpeed.magnitude)`. The floor of 24 is why an SSJ from a standstill reads as +24.75 u/s onto a base of 24.
- **`NewMovement.jumpCooldown`** — private; set by `Jump`, `WallJump` and `Launch`, cleared by the `JumpReady` invoke (0.2 s, 0.1 s after a wall jump). A macro precondition.
- **`NewMovement.wcGroup`** — private `WallCheckGroup`. `TryGetActiveInstance(out WallCheck)` is the wall macro's precondition and the source of `wall_available`; `CheckForEnemyCols()` separates a wall jump from an enemy step. A `WallCheck` is a component, not a distance, so no raycast can substitute.
- **`NewMovement.boostLeft`** (private) — dash i-frames remaining; `Dodge()` sets layer 15 while it is positive, and `GetHurt` returns immediately for `invincible && layer == 15 && !ignoreInvincibility`. **`dashStorage`** (private) decays it in `FixedUpdate`.
- **`NewMovement.slamStorage`** (private), **`slamForce`**, **`slamCooldown`**, **`preSlideSpeed`**, **`falling`**, **`jumping`**, **`boost`**, **`currentWallJumps`**, **`dodgeDirection`**, **`preDashSpeed`** — public.
- **`NewMovement.TryStartSlam`** is far fussier than folklore: it needs `Slide.WasPerformedThisFrame` while airborne **and** nothing within 3 m below **and** `fallTime > 0.5` **and** `slamCooldown == 0` **and** `!gc.heavyFall`. A jump on flat ground can never satisfy it.
- **`HandleInputs` ordering decides which jump you get.** `flag2 = !gc.onGround && (gc.canJump || wcGroup.CheckForEnemyCols())`; the first block fires on `flag2` or on `!falling` and calls `Jump()`, which sets `jumpCooldown` — so the **wall-jump block below it is skipped entirely**. That is why `coyote`, `not_falling` and `enemy_step` are wall-macro refusals rather than degradations.
- **`GroundCheck`** — `onGround`, `canJump`, `heavyFall`, `superJumpChance`, `extraJumpChance`, `bounceChance`, `sinceLastGrounded` (a `TimeSince`), all public.
- **`Revolver.gunReady`** — private, read through the currently held weapon's component. See `weapon_tech` in `docs/protocol.md`.
- **`WeaponCharges`** — a `MonoSingleton` whose charge fields are all public: `rev0charge`, `rev1charge`, `rev2charge`, `shoAltNadeCharge`, `shoSawCharge`, `raicharge`, `rocketcharge`, `rocketFrozen`, `rocketFreezeTime`.
- **`CoinTracker.revolverCoinsList`** and **`ObjectTracker.grenadeList` / `cannonballList`** — public lists the game already maintains, filtered to the player's own (`Coin.shotByEnemy` false, `Grenade.enemy` false). `Grenade` exposes `rocket`, `frozen`, `playerRiding`, `rideable`, `rb`.
- **`GunControl.SwitchWeapon(int targetSlotIndex, int? targetVariationIndex = null, ...)`** — public, and what the game's own slot keys call. Used directly for the `variant` action.
- **`PrefsManager.GetBool("ssjIndicator")`** — postfixed to read true while in control under the `ssj_indicator` config, which makes `TrySSJ` print its bucket bar and `+{n}u/s` as a subtitle. The stored preference is never written.
- **`InputSystem.QueueStateEvent<TState>(InputDevice, TState, double time = -1)`** — the timestamped overload, present in the installed `Unity.InputSystem.dll`. **Verified in game 2026-09-20: an explicit timestamp reaches `ctx.time` unchanged** — a requested 12 ms gap measured 11.999–12.000 ms across 50 trials. `InputSystem.settings.updateMode` is **`ProcessEventsInDynamicUpdate`** on this build, so a future-dated event is processed in the current update rather than time-sliced.
- **Serialized values that cannot be read from decompiled C#**, measured in game 2026-09-20 and reported in `hello.diag`: `walkSpeed` **750**, `jumpPower` **90**, `wallJumpPower` **150**, `Time.fixedDeltaTime` **0.008**. These confirm the derived SSJ bonuses exactly: `0.5 × 750 × 2.75 × 3 × 0.008 = 24.75` u/s for a ground SSJ and `37.125` for a wall one.

## Campaign
- **Exit:** `FinalPit` is a trigger baked into the scene. Entering it sets `NewMovement.levelOver`, clears `activated`, calls `StatsManager.StopTimer()` and sends results 5 s later. Decoys carry `fakeEnd`, `secondPit` or `rankless`. The pit can sit in a room that starts inactive, so the mod searches with `FindObjectsOfType<FinalPit>(true)`. `targetLevelName` is the scene it leads to; a secret level's name ends in `-S`. A level can hold several real-looking pits (0-2: one to `Level 0-3` and one to `Level 0-S`; 1-1: one to `Level 1-2` and two to `Level 1-S`), all inactive at load, so the mod filters the secret targets out and then prefers the next mission in campaign order. A **Prime Sanctum** target is `Level P-1` / `Level P-2` (6-2 ships two of them, 3-1 one) and is filtered out the same way; an **act finale's** real exit targets `Intermission1` / `Intermission2` (3-2 and 6-2) rather than a level, so an `Intermission*` target counts as leading onward. 8-4's pit targets `EarlyAccessEnd`, which is neither.
  - **The chosen pit's OBJECT does not survive the level load; the decision does.** When the exit's room belongs to a checkpoint whose `Start` has not run yet, the first scan picks the original — and `CheckPoint.Start` then clones that room and banishes the original +10000 on X (see Room templates below), leaving the frozen reference pointing at a pit 10 km away while the real trigger stays put. Measured on `Level 0-2`: the exit read `(9801, -86.1, 277)` once checkpoint `-55,-11,277` activated, against a true pit at `(-199, -86.1, 277)`. Since v0.7.1 `CampaignObserver.ResolveExit` re-resolves on every `Scan`: the *rule* still runs once per level load (its rank includes `activeInHierarchy`, which changes as rooms stream in, and every gate's hop count is measured from the chosen pit's room), but what it freezes is the pit's `targetLevelName` plus the position it held when it was picked, and each scan re-attaches that verdict to whichever live pit sits nearest that anchor. The clone is instantiated at the original's exact position, so it is 0 m away and the banished twin 10,000 m away. Python's `ExitGuard` is the older stopgap and stays: it accepts a report a whole multiple of 10,000 back toward the anchor, which is exactly what the mod now sends.
- **Room templates:** `CheckPoint.Start()` adds each of `rooms` to `defaultRooms`, clones it in place (`newRooms`), disables the original and moves it +10000 on X relative to wherever it was. A respawn (`ResetRoom`) destroys the live copy and instantiates the template again at the live copy's position. Inactive-object searches skip anything under a `defaultRooms` entry. **Consequence for any graph built out of room objects:** the same physical room is a different object across a respawn, so rooms must be identified by their rounded world position, never by reference. The position key also separates the banished templates by itself (+10000 X).
- **Checkpoints:** `CheckPoint.activated`, `ActivateCheckPoint()`, `StatsManager.currentCheckPoint`. `StatsManager.Restart()` respawns at the current checkpoint and adds 1 to `restarts` (`CheckPoint.OnRespawn` unlocks `doorsToUnlock` and resets the rooms it owns), or reloads the scene when there is none. `startOff` checkpoints start activated.
- **Timer:** `StatsManager.seconds += Time.deltaTime * GameStateManager.Instance.TimerModifier` while `timer`. Respawns do not reset it and cutscenes do not stop it.
- **Arenas:** `ActivateNextWave` (`lastWave`, `activated`, `deadEnemies`, `enemyCount`). Enemies find their wave with `GetComponentInParent<ActivateNextWave>()`. `activated` goes true once `deadEnemies` reaches `enemyCount`. A non-last wave then unlocks its `doors`, spawns the next wave and destroys itself; the last wave invokes the private `EndWaves()` repeatedly (once per entry of `doors`, unlocking it and opening `doorForward`, then a final call that destroys the component).
- **Doors:** `Door.locked`, `Door.open`, `Door.Unlock()` (clears `locked`, opens when `openOnUnlock`).
  - **`activatedRooms` (`GameObject[]`) is the level's room graph.** `Door.Open()` calls `SetActive(true)` on every entry, which is how rooms ahead of the player (and the exit's own room) come up. A door listing two or more rooms connects them, and a breadth-first search from the exit's room orders every such door in 0-1 (11 doors, 0-9 hops), 0-2 (17, 0-7), 0-3 (12, 0-6), 0-4 (7, 0-5) and 1-1 (13, 0-5). It fails in 0-5, where no room on the pit's ancestor chain is one of those rooms. Only the rooms of two-or-more-room doors may be nodes: several levels have a one-room door pointing at a GameObject literally named `Pit` on the exit's own chain, which would otherwise make every gate 0 hops.
  - **A Normal door moves its OWN transform while it opens.** `Door.Update` runs `transform.localPosition = MoveTowards(..., targetPos, ...)` with `targetPos = openPosRelative = closedPos + openPos`. Measured from the scene files, **every** such door on 0-1 (11/11), 0-2 (17/17), 0-3 (12/12), 0-4 (7/7) and 0-5 (3/3) is `doorType 0` with `openPos = (0, 5.75, 0)`; 1-1's 13 are `doorType 1`, whose `Update` returns early. The closed position is `gotPos ? parent.TransformPoint(closedPos) : transform.position` (`closedPos` is a **local** position set in the private `GetPos()`; both it and `gotPos` are public).
  - The `NavMeshObstacle` sits on the `Door Object` child, not on the `Door` component's GameObject, and the `DoorController`s are siblings under a `Door (Large) With Controllers (N)` parent. `Door.Awake` finds them with `transform.parent.GetComponentsInChildren<DoorController>()` for a Normal door — **without** `includeInactive`, so `Door.docons` is empty for exactly the doors whose controller an `ActivateArena` has not switched on yet.
  - `DoorController.Update` opens on `playerIn || enemyIn` (type 0 is an 8x6x6 proximity trigger) and `Close()`s as soon as both go false, and `Door.Open()` force-closes every other open door with a type-0 controller and no enemy in it. So `Door.open` means "currently open or opening", never "has been passed".
- **Altars and carryable items:** `ItemPlaceZone` (`acceptedItemType`, `doors`, `reverseDoors`, `activateOnSuccess`/`deactivateOnSuccess`) and `ItemIdentifier` (`itemType`, `pickedUp`, `infiniteSource`, `ipz`). `ItemType` is `None, SkullBlue, SkullRed, SkullGreen, Readable, Torch, Soap, CustomKey1..3, Breakable`.
  - `ItemPlaceZone.CheckItem` decides "filled" with `GetComponentInChildren<ItemIdentifier>()` **without** `includeInactive` and a type test; on success it opens every `doors` entry and **closes** every `reverseDoors` entry, on failure (the item taken back out) it closes `doors` and re-opens `reverseDoors`. `Start` sets `ipz` on the placed item, so `ipz` is null for a pedestal skull whose room has not switched on yet.
  - `ItemPlaceZone.ColorDoors` (from `Start`) calls `Door.AltarControlled()`, which **deactivates every `DoorController`** of the doors it drives. So a skull-locked door reports `open: false, locked: false, controller_active: false` — indistinguishable from a door an arena holds shut, which is why the obs carries `gates[].needs_item`.
  - An altar's doors are usually **one-room streaming doors**, which the two-or-more-rooms gate test rejects; the mod appends them as `altar_only` gates so a skull leg is visible to the route at all.
  - Levels ship **coincident duplicate zones and items**: one of each pair sits under a permanently disabled parent and can never activate. Counting inactive GameObjects on an object's own chain separates them — one is the room switch, two is a dead branch.
- **Pick up and place: `Punch`.** `Punch.ActiveFrame` `CheckSphere`s the camera position and otherwise raycasts 4 m from `cc.GetDefaultPos()` along camera forward against `environmentMask` (which `Awake` builds as `LayerMaskDefaults.Get(LMD.Environment) | 0x400000`, i.e. layer 22 is included), then calls `AltHit(hit.transform)`. `AltHit` acts only on **layer 22**: holding + the target has `ItemPlaceZone`s → `PlaceHeldObject`; not holding + the target has an `ItemIdentifier` → `ForceHold`. It **returns immediately when the hit transform itself carries an `ItemIdentifier` while the player is holding**, so a placement punch must hit the zone's own cube, not a skull already resting on it. The block sits outside the `FistType.Standard` guard, so either fist works. **So the existing `punch` button is the whole pick-up/place action — no new input is needed.**
  - Two hazards for a carry: `Punch.ActiveStart` **throws** the held item when the first active frame did not place it, and punching a filled altar calls `ForceHold`, which re-runs `CheckItem` and **closes the door that altar opened**.
  - **`ActiveStart`/`ActiveEnd` are Unity AnimationEvents** — grepped, no C# caller exists for either. `ActiveFrame` only runs while `ActiveStart` has set `activeFrames`, so with rendering disabled the fist Animator would be culled and nothing could ever be picked up. `TrainingSpeed.ForcePlayerAnimators` sets `AlwaysAnimate` on every Animator under `FistControl` and `CameraController` for exactly this reason.
  - **The arms are rebuilt mid-level, so that walk cannot be cached on a child count.** `FistControl.ResetFists` (`decompiled/FistControl.cs:217-256`) destroys every entry of `spawnedArms` and instantiates the replacements as children of the same `FistControl` (`:231, :283, :300, :307`). Prefs do not change mid-level, so the usual result is N arms replaced by N arms: the child count is unchanged, both singleton instance ids are unchanged, and the Animators are all new. `ResetFists` runs from `WeaponPickUp.cs:104` (walking over an arm pickup), `PlayerLoadout.SetLoadout`, `PlayerLoadoutTarget.CommitLoadout`, `VariationInfo.cs:199,247` and `FistControl.TutorialCheckForArmThatCanPunch` (a UnityEvent target, no C# caller); the loadout paths can also swap which arm prefabs exist without changing the count. `ForcePlayerAnimators` therefore keys its cache on a hash over the two instance ids **and every direct child's instance id**, and additionally re-walks whenever any Animator it forced has become null (a destroyed `UnityEngine.Object` compares equal to null), which also catches a replacement deeper than a direct child. Without that, one arm pickup silently disables skull carrying for the rest of the level load and nothing logs.
- **NavMesh:** enemies use `NavMeshAgent`, so campaign scenes have a baked ground mesh (`UnityEngine.AIModule.dll`: `NavMesh.SamplePosition`, `NavMesh.CalculatePath`, `NavMeshPath`). Jumps and gaps are not linked.
- **Level start:** the player drops in under the `"pit-falling"` game state (`PlayerActivatorRelay`), which locks the camera and cursor but not player input; `PlayerActivator` pops it and sets `NewMovement.activated` on landing. `GameStateManager.Instance.PlayerInputLocked` is set only by game states registered with `playerInputLock` (the pause, cheat and spawn menus, the console, `AutoRegisterState` objects), so the campaign block's `input_locked` also checks `!activated`.
- **Difficulty:** `PrefsManager.GetInt(string key, int fallback = 0)` (instance) with `"difficulty"`: 0 Harmless, 1 Lenient, 2 Standard, 3 Violent, 4 Brutal. Enemies and `NewMovement` read it at scene start.
- **Gear:** `GameProgressSaver.CheckGear(string gear)` (static) reads the int field of `GameProgressMoneyAndGear` with that name (`rev0..rev3`, `revalt`, `sho0..3`, `shoalt`, `nai0..3`, `naialt`, `rai0..3`, `rock0..3`, `beam0..3`, `arm1..3`), 0 when missing. `GearCheckEnabler` switches scene objects on owned gear, so with `unlock_all_gear` a level looks the way it does for a player who owns everything. `WeaponPickUp` skips its prefs and save writes when the gear already reads as owned.
- **Death:** `NewMovement.GetHurt(int damage, bool invincible, float scoreLossMultiplier = 1f, bool explosion = false, bool instablack = false, float hardDamageMultiplier = 0.35f, bool ignoreInvincibility = false)` sets `dead` and clears `activated` at 0 hp, and returns early when `dead` or `levelOver`. Outside Cyber Grind, `StatsManager.Update` calls `Restart()` by itself when the player is at 0 hp and Fire1 is newly pressed (or R), unless paused; the pause menu's `RestartCheckpoint` and the debug console call it too. While the AI has control `CampaignPatches` blocks every `Restart` except the bridge's own checkpoint reset, so a death always stays visible until Python respawns.
- **Rank:** `timeRanks`, `killRanks` and `styleRanks` hold 4 thresholds each. Per category, count the thresholds met in order (time: `seconds <= t`; kills and style: `value >= t`), stopping at the first miss; meeting all 4 scores 4. The total is the sum minus `restarts`, floored at 0. 12 with no cheats is P, otherwise `RoundToInt(total / 3)` indexes D, C, B, A, S.
- **Mission numbers** (`GetMissionName`): 1-5 `Level 0-1`..`Level 0-5`, 6-9 `1-1`..`1-4`, 10-13 `2-1`..`2-4`, 14-15 `3-1`, `3-2`, 16-19 `4-1`..`4-4`, 20-23 `5-1`..`5-4`, 24-25 `6-1`, `6-2`, 26-29 `7-1`..`7-4`, 30-33 `8-1`..`8-4`, 34-35 `9-1`, `9-2`.

## Steam: `Facepunch.Steamworks.Win64.dll`
Audited 2026-09-17 for v0.7.1's `-aibridge-nosteam`. Everything below is from the shipped assembly and `decompiled/`.
- **Registering with Steam happens in exactly one place.** `Steamworks.SteamClient.Init(uint appid, bool asyncCallbacks = true)` sets the `SteamAppId`/`SteamGameId` environment variables, calls `SteamAPI.Init()` (this is what tells a running Steam client that app 1229490 is live), sets `AppId`, opens ~20 interfaces and sets the private `initialized` flag. `SteamClient.IsValid` is that flag. The game calls it once, from `SteamController.Awake` (`decompiled/SteamController.cs:54`) — inside a `try`/`catch` that already treats "Steam isn't there" as normal and logs `Couldn't initialize steam`. So a Harmony prefix returning false is enough: `IsValid` stays false and the caller sees a successful call.
- **Nothing else registers.** Grepped for `SteamClient.`, `SteamApps`, `SteamUser`, `SteamFriends`, `Steamworks.` and `RestartAppIfNecessary` across `decompiled/`: the only hits are `SteamController`, `PresenceController`, `LeaderboardController`, `FishLeaderboard`, `LevelEndLeaderboard`, `LevelSelectLeaderboard`, `FinalCyberRank`, `WorkshopHelper` and `Sandbox/StatsDisplay`. **`SteamClient.RestartAppIfNecessary` is never called**, and the game ships **no `steam_appid.txt`** — Facepunch's own `Init` is what sets the appid environment variable, which is why launching the exe directly works at all.
- **Every consumer gates itself on `IsValid`**, so they all switch off by their own code rather than needing another patch: rich presence (`SteamController.FetchSceneActivity`, `UpdateWave`), user stats (`UpdateTimeInSandbox`, `AddToStatInt`, `GetSandboxStats`), UGC playtime (`PresenceController.Start`'s `SteamUGC.StopPlaytimeTrackingForAllItems`), `SteamClient.Shutdown` on quit, and `LeaderboardController.LeaderboardsSupported`. The two `SteamClient.SteamId` reads that are not directly gated sit behind `LeaderboardsSupported` (`GetOwnLeaderboardScore`) and behind `SafetyPatches`' fish-size block (`:310`).
- **Consequence:** with the flag on, the game boots and plays normally, Steam credits no playtime and does not list ULTRAKILL as running. Steam's own belief is readable at `HKCU\Software\Valve\Steam\Apps\1229490\Running`.
