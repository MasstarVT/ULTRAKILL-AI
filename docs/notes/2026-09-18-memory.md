# Memory engineering, 2026-09-18

The box (32 GB RAM, 28 GB page file, **~60 GB commit limit**) ran out of committed memory three times:

| when | what | evidence |
|---|---|---|
| 2026-09-17 09:50 | one `python.exe` at **70 GB virtual** | Windows resource-exhaustion event; an agent-run offline analysis script |
| 2026-09-18 01:40 | one `python.exe` at **55 GB virtual** | same, same cause |
| 2026-09-18 12:38 | three `ULTRAKILL.exe` at **5.8-6.1 GB commit each** | killed the 12-game run, the driver *and* the desktop session |

Commit, not working set, is what runs out, and everything below is measured in committed private bytes.

---

## 1. Where the memory actually was

### 1.1 numpy's BLAS thread pool: 785 MB per process, for 13 MB of working set

The single largest finding, and it was hiding in plain sight. Measured on this box (24 logical CPUs,
numpy 2.5.3), private bytes after a bare import in a fresh interpreter:

| import | private | working set |
|---|---|---|
| `pass` | 8 MB | 15 MB |
| `import numpy` | **793 MB** | 28 MB |
| `OPENBLAS_NUM_THREADS=1; import numpy` | **18 MB** | 26 MB |
| `OPENBLAS_NUM_THREADS=2; import numpy` | 52 MB | 26 MB |
| `import torch` | 959 MB | 203 MB |
| `from stable_baselines3.common.monitor import Monitor` | 969 MB | 215 MB |
| `import ultrakill_ai.env` | 801 MB | 40 MB |

OpenBLAS reserves a per-thread buffer pool when the DLL loads — ~34 MB a thread (the 2-thread row is the
measurement), ~800 MB across 24 CPUs. It is **committed and charged in full**, and almost never touched,
which is why the working set stayed small and nobody noticed. Nothing in this project multiplies a matrix
big enough to want it: the workers pack a 479-float observation and the helpers read JSON.

`OPENBLAS_NUM_THREADS` only, never `OMP_NUM_THREADS` — the latter is torch's knob too and setting it to 1
costs the trainer 2.5x per update (the KMP_BLOCKTIME note in `ultrakill_ai/training.py`).

### 1.2 spawn re-executes `scripts/train.py` in every worker

`SubprocVecEnv` uses multiprocessing *spawn*, and a spawn child runs the parent's `__main__` file top to
bottom (as `__mp_main__`, via `runpy.run_path`) before it unpickles anything. `scripts/train.py` imported
torch and stable_baselines3 at module level, so all twelve workers paid for a deep learning stack: **+175 MB
each** on top of §1.1.

And SB3 pickles each `env_fn` with cloudpickle. A closure is pickled by value but the globals it *names* are
pickled by reference, so `Monitor(UltrakillEnv(cfg))` made the worker import `stable_baselines3` — whose
package `__init__` imports PPO, hence torch — no matter how light `train.py` became.

### 1.3 the package `__init__` pulled `env` into everything

`ultrakill_ai/__init__.py` did `from ultrakill_ai.env import ...` at the top, so importing
`ultrakill_ai.times` for a leaderboard string, or `ultrakill_ai.windows` for a monitor rectangle, imported
gymnasium and numpy. That is the whole of why `dashboard.py`, `campaign_driver.py`, `post_times.py` and
`mem_guard.py` each held **0.75 GB of commit for 0.04 GB of working set**.

### 1.4 the games leak, and fast

Measured on the live 12-game run, from the guard's own log and from `GetProcessMemoryInfo`:

| time | games total | fattest | system commit |
|---|---|---|---|
| 17:06 (fleet just launched) | 14.5 GB | 1.2 GB | 55% |
| 17:09 | 17.9 GB | 1.5 GB | 80% |
| 17:11 | 18.4 GB | 1.6 GB | 82% |
| 17:23 | 20.3 GB | 1.8 GB | 85% |
| 17:34 | — | — | 88% |

**~1.2-1.4 GB per game per hour** while training, from a 1.2 GB boot. Extrapolated that is 1.2 + 5.5×1.3 ≈
**6.4 GB after 5.5 h**, against the 5.8-6.1 GB the 12:38 crash event actually recorded. The leak is the
games, it is continuous, and it is the reason nothing had noticed it before the freeze fixes landed: until
2026-09-17 the games were restarted every hour or two by crashes and pauses.

## 2. What changed

### 2.1 Light workers and light helpers (`ultrakill_ai/procmem.py`, `envfactory.py`, `training.py`)

* `procmem.cap_blas_threads()` sets `OPENBLAS_NUM_THREADS=1` and **returns whether it was in time** (numpy
  not yet imported), so the ordering is testable rather than assumed. Called as the first statement of every
  light entry point: the `__mp_main__` branch of `scripts/train.py`, and `dashboard`, `campaign_driver`,
  `post_times`, `supervise`, `games`, `mem_guard`, `eval`, `full_run`, `build_routes`, `replay_curriculum`,
  `run_capped`.
* `scripts/train.py` is now a launcher whose module body imports nothing heavier than `pathlib`. The trainer
  is `ultrakill_ai/training.py`, imported only on the branch that runs it. `import train` still re-exports
  everything the tests use, on a branch a worker never takes.
* `ultrakill_ai/envfactory.py` holds `make_env` and `EpisodeMonitor`, so every global the pickled closure
  names resolves in a light module.
* `EpisodeMonitor` is SB3's `Monitor` for the one configuration this project uses (no csv, early resets
  allowed, no reset keywords), reimplemented without the SB3 import. It produces a **byte-identical**
  `info["episode"]` — same keys, same `round(., 6)`, same float64 sum — pinned by
  `test_the_in_package_monitor_matches_sb3s_monitor_exactly`. SB3's own `VecMonitor` in the trainer process
  was considered and rejected: it accumulates the return in float32 and times episodes from the vec env's
  construction rather than each env's, which would have moved two numbers with years of history.
* `ultrakill_ai/__init__.py` is lazy (PEP 562 `__getattr__`). `from ultrakill_ai import UltrakillEnv` still
  works; nothing is paid by a process that never touches it.

**Measured**, fresh interpreter, exactly the sequence a spawn worker performs:

| | private |
|---|---|
| worker's import set, before | **971 MB** |
| worker's import set, after | **26 MB** |
| `import ultrakill_ai` | 9 MB |
| `dashboard` / `supervise` / `games` / `mem_guard` | 9-13 MB (was ~750) |
| `campaign_driver` / `post_times` | 20-22 MB (was ~750) |

### 2.2 Guard hardening (`scripts/mem_guard.py`, `ultrakill_ai/env.py`)

* **The per-game limit is derived, not a constant.** `procmem.derive_game_limit` = *the freshest booted copy
  running* + `--growth-gb` (1.0), clamped to `MAX_LIMIT_GB` 3.0 and ignoring samples under `MIN_FRESH_GB`
  0.8 (a half-booted copy sits at 56-250 MB and believing it would put the limit under the boot size and
  recycle the fleet forever). A constant cannot do this job: a fresh game was ~1.0 GB before mod 0.7.x and is
  1.2-1.5 GB now. `--game-limit-gb N` still forces a fixed limit. The system threshold
  (`--commit-limit-frac` 0.93) is unchanged.
* **One line per recycle, with both sizes**: `port 47803 is listening again: 2.61 GB -> 1.24 GB (freed
  1.37 GB), system commit 74%`. That line is also the freshest baseline the derived limit will ever see.
* **The env recycles its own game at an episode boundary** (`EnvConfig.game_memory_growth_gb`, 0 = off).
  `UltrakillEnv.reset()` reads the fleet, derives the same limit from the same function, and if its own game
  is over it, restarts it through the **existing relaunch rung** — same cross-process permits, same per-port
  stagger, same boot gate. The difference from the external guard is *when*: the guard kills a game at an
  arbitrary moment and the env truncates that episode as `bridge_reset`; this fires inside `reset()`, where
  the episode has already ended and a level load is about to happen anyway. **Same boot cost, no episode
  lost.** It is inert without `bridge_relaunch`, which only `train.py` sets, so no eval or test can recycle a
  game. A freshly booted game still over the limit latches the mechanism off rather than relaunching forever,
  and every failure is swallowed — a memory optimisation may not become a new way for a reset to die.

### 2.3 A cap for offline scripts (`scripts/run_capped.py`)

```
python scripts/run_capped.py --max-gb 8 -- python scripts/build_routes.py --validate
```

A Windows Job Object with `JOB_OBJECT_LIMIT_PROCESS_MEMORY` + `JOB_OBJECT_LIMIT_JOB_MEMORY` +
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. The launcher assigns **itself** to the job and spawns the command
normally — a child inherits its parent's job, which avoids the CREATE_SUSPENDED / AssignProcessToJobObject /
ResumeThread dance entirely. Proven in `tests/test_run_capped.py`: a child asking for 2 GB under a 0.5 GB cap
dies with `MemoryError`, a **grandchild** cannot escape the tree limit, the exit code is the command's own,
and the test process itself grows 0.1 MB.

`build_routes.py` and `replay_curriculum.py` now **refuse to start above 85% system commit**
(`procmem.refuse_if_commit_high`), naming `run_capped.py` in the refusal and honouring
`ULTRAKILL_AI_IGNORE_COMMIT=1`. The live run alone sits near 80%, so anything above 85% is either a second
analysis script or a fleet that has already leaked.

## 3. The mod and the game-side leak

An audit of every file in `mod/UltrakillAIBridge` found that **the mod retains almost nothing across scene
loads**, so no mod-side cache fix can recover gigabytes:

* `CampaignPatches.clearedArenas` / `unlockedDoors` hold **strings**, not object references, and are cleared
  on every single-mode `sceneLoaded`. Not a leak.
* `CampaignObserver`'s caches (pits, checkpoints, doors, templates, gates, altars, items, the room graph, the
  door-key tables, `chosenExit`) are all cleared at the top of the method that refills them, and `Build`
  forces a rescan on a scene-handle change. Not a leak. One narrow case: leaving the campaign for a menu or
  intermission keeps the previous level's destroyed wrappers referenced, bounded at <100 KB.
* `TrainingSpeed.forcedAnimators` is restored and cleared before every re-walk, with a destroyed-Animator
  check. Not a leak — this one was designed against exactly this failure and the design holds.
* `Plugin`'s two event subscriptions and its `DontDestroyOnLoad` host are created once in `Awake`.
* No `Texture`, `RenderTexture`, `Material` or `Mesh` is created anywhere in the mod.
* **`TrainingSpeed.disabledCameras` is the one never-cleared cross-scene collection** — genuinely a leak, and
  worth tens of bytes per scene load. Under 100 MB over a whole session. Fix it because it is three lines,
  not because it explains anything.

Two things that *are* of the right order of magnitude, neither of them a retention bug:

1. **Per-step JSON churn.** The mod builds a fresh Newtonsoft `JObject` tree and serializes it ~20x a second
   forever. Grounded on the measured wire size (11 gates is 1.5 KB of a 3.6 KB obs line), the token graph is
   15-20x that, so **~1.8 MB/s per game, ~35 GB allocated and freed per game per 5.5 h session**. Unity 2022.3
   Mono uses the **non-compacting Boehm GC**, which does not return address space in practice; 35 GB of churn
   across mixed size classes grows the heap's high-water mark monotonically.
2. **The game never sweeps assets on a level change.** `grep -rl "UnloadUnusedAssets\|GC.Collect"` over all
   1178 decompiled files hits exactly one, `SandboxSaver.cs` — nothing on the level-change path.
   `SceneHelper.LoadSceneCoroutine` discards its `Addressables.LoadSceneAsync` handle, and
   `SceneHelper.SetUpFootstepPhysicsScene` rebuilds a whole parallel physics scene per load, duplicating every
   qualifying `MeshCollider` (native PhysX cooked-mesh memory). 30 curriculum levels x ~150 MB of level assets
   ≈ 4.5 GB on a 1.3 GB base ≈ the 5.8 GB observed. A human loads 10-20 scenes a session, not 40-150.

**Those two need opposite fixes, and source reading cannot choose between them.** So the mod now carries both
the measurement that chooses and the fix for the more likely one. **Compiled clean (0 warnings, 0 errors) and
NOT installed** — the twelve running games hold the DLL open, so this waits for the next pause:

| change | file | what it does |
|---|---|---|
| `mem` observation block | `Obs/ObservationBuilder.cs` | `Profiler.GetMonoUsedSizeLong` / `GetMonoHeapSizeLong` / `GetTotalAllocatedMemoryLong` / `GetTotalReservedMemoryLong`, behind the config key `report_memory` (default **off**). This is the measurement that decides between §3.1 and §3.2. Additive JSON, so an older Python ignores it. |
| the asset sweep | `Env/EpisodeController.cs` | `SweepAssetsDone()`: one `Resources.UnloadUnusedAssets()` + `GC.Collect()` per reset, awaited across frames **before the reset reply is sent**, so the 100 ms - 2 s stall is paid inside a reset the client is already blocked on. Gated on `InControl` **and** the config key `unload_assets_on_reset` (default on), so a human's game is never touched. `resetTimeoutSeconds` still bounds the whole reset, and `sweep` is cleared when a reset begins so one reset gets exactly one sweep. |
| `disabledCameras` pruned | `Env/TrainingSpeed.cs`, `Plugin.cs` | `TrainingSpeed.OnSceneLoaded()` drops destroyed camera wrappers, called from the existing single-mode `sceneLoaded` hook beside `CampaignPatches.OnSceneLoaded()`. The mod's one genuine never-cleared cross-scene collection. Worth <100 MB a session; fixed because it is three lines. |
| `Vec` de-boxed | `Obs/ObservationBuilder.cs` | `new JArray(v.x, v.y, v.z)` binds `JArray(params object[])` — an `object[3]` plus three boxed floats per call, ~40 calls a step. Replaced with three explicit `JValue`s. Cuts churn; changes no output. |

**The measurement that chooses**, once the DLL is installed: log the four `mem` counters next to the process's
private bytes over 60 fresh level loads. `mono_heap` tracking private bytes means §3.1 (the fix is to stop
building a `JObject` tree and write straight to the client's `StreamWriter` through a long-lived
`JsonTextWriter`); `native_reserved` tracking it means §3.2, and the sweep already shipped above is the fix.

## 4. Pause checklist — what to do at the next pause, in order

The games hold the mod DLL open, so all of this needs the run stopped.

1. `New-Item python\runs\specialists\DRIVER_PAUSE`, stop the driver, `python scripts/games.py stop`.
2. **Build and install the mod**: `cd mod/UltrakillAIBridge && dotnet build -c Release`.
3. **Measure which of §3's two mechanisms it is** — the mod reports `mem` in the observation
   (`Profiler.GetMonoUsedSizeLong` / `GetMonoHeapSizeLong` / `GetTotalAllocatedMemoryLong` /
   `GetTotalReservedMemoryLong`). Start ONE private instance on port 47812 and log those four next to
   `procmem.private_bytes` across 60 fresh loads of one level:
   * `mono_heap` tracking private bytes ⇒ the JSON churn (§3.1). The fix is to stop building a `JObject` tree
     and write the observation straight to the client's `StreamWriter` through a long-lived `JsonTextWriter`.
   * `native_reserved` tracking it ⇒ assets and bundles (§3.2). The fix is the asset sweep, below.
4. **The asset sweep**, gated on `EpisodeController.InControl` and a config key so a human's game is never
   touched: after a reset settles, `yield return Resources.UnloadUnusedAssets(); GC.Collect();` on the
   existing `BridgeRunner` coroutine host, before the reset reply is sent — the stall is then paid inside a
   reset Python is already waiting for. Cost 100 ms - 2 s per level load, against an OOM every 5.5 h.
5. **Verify**: repeat step 3's measurement before and after. The acceptance bar is private bytes after 60
   fresh loads, and the pass condition is that it stops rising monotonically.
6. `Remove-Item DRIVER_PAUSE` and restart the driver.

**Until the mod fix lands, the recycle interval the guard needs**, from §1.4's measured ~1.3 GB/game/hour and
a 1.2 GB boot: a game reaches the derived limit (fresh + 1.0 GB) in **roughly 45 minutes**. With 12 games and
the guard's 240 s cooldown that is ~16 recycles an hour against a capacity of 15 — i.e. the external guard
alone is marginal, which is exactly why §2.2 added the episode-boundary recycle in the env, where a recycle
costs a boot instead of an episode.
